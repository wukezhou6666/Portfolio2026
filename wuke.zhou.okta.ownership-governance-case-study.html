Challenge Framing

Design Decisions That Define Crawl Stage

Challenge 01
Entry Point
"Where should users access this new feature?"

The integration point determines the mental model. Get it wrong and users won't find the feature — or worse, will have the wrong frame for it.

Challenge 02
Scalability
"How do we handle multiple resource types without poor UX?"

Access Cert was single-type. Ownership Cert requires multi-type support. A structural decision that must be made now before I compound technical debt.

Challenge 03
Reviewer Scope
"Who should be asked 'Are you the owner?' and what if they say no?"

Unlike access, ownership is power transfer. I designed a fallback mechanism that guarantees every resource ends up with an accountable owner — regardless of how many reviewers decline.

Each challenge has trade-offs. My solutions balance Dell's immediate needs with the long-term platform vision — and I'll walk through the reasoning on each.

Scalability

How to Handle Multiple Resource Types Without Breaking UX?

The Problem

Access Certification only handles a single resource type at a time in resource campaign.

Ownership Validation requires multi-type support — Application, group, collection, AI Agent, Service Accounts and more as the product grows.

If I don't make the right structural decision now, UX degrades as resource types grow and technical debt compounds.

Reviewer Scope

Why Ownership Requires Enforced Fallback Mechanism

Access Certification Ownership Validation
Revoke Result User immediately loses access. Low-stakes — usually recoverable in the next review cycle. Owner designation is removed. Resource enters a "no owner" state — governance breaks until resolved.
Reassign Result Review task is passed to the next reviewer. Access itself is unchanged — only who certifies it changes. Ownership is actually transferred to another person. The new resource owner now controls all access approvals and compliance reviews for the resource.
Resource Status Resource stays fully operational. Other users' access is completely unaffected.
  • Immediate: Access requests have no one to approve them. Compliance cycles have no one to run them. Both workflows break.
  • Systemic: Unowned resources accumulate at scale — expanding the attack surface and eroding company-wide security posture.
Reviewer Scope Cont.

How Different Reviewer Type Change Reviewer Flow's Decision Path

1
Resource Owner
"Are you the owner of this resource?"
Yes → End. No → Specify correct owner and continue to Path 2.
2
Reassigned Owner
"Are you correctly assigned as owner?"
Anti-loop protection. Yes → End. No → Escalate to fallback reviewer. Cannot loop back to Path 1.
3
Fallback Reviewer (Campaign Creator / IAM Admin / GRC Analyst)
"Find and assign the actual owner."
High-authority reviewer. MUST complete — no further escalation possible. Terminates the chain.
4
Manager Audit
"Who is the owner of this resource?"
Third-party attestation. Unlike Path 1 where the owner self-attests, the manager independently verifies ownership from the outside — providing an external audit layer.
Design Principle: I structured the paths around two reviewer types — high-intent (Paths 1–2, directly involved) and high-authority (Paths 3–4, final decision makers) — so that every resource must have an owner at the end of the chain.
Reviewer Scope · Design Exploration

Design Exploration on Reviewer Flow

Once I mapped out how different combinations of reviewer identity and action affect the outcome, I explored four distinct reviewer flow designs — and evaluated each against the dimensions that matter most for this product.

Exploration Simplicity Speed Safety Effort to Eng
My Recommendation High High Mid Extra Low
Description

Built on the assumption that resource owners represent the majority of reviewers, the solution is designed to help users make the quickest ownership decision possible.

Pros
  • Surfaces only the minimum information needed to judge ownership — easier to understand and faster to act on.
  • Reduces clicks; provides help text for contextual understanding.
  • Highly backward compatible, yet has enough room to grow further.
Cons
  • A middle-ground solution — conservative by design.
2-Step Verification Mid Mid Mid–High Mid
Description

A two-step process where users confirm ownership before proceeding to access review.

Pros
  • User understands better what's the consequence of the action.
  • User knows clearly this is not an access certification campaign.
  • A sandbox stage becomes a middle ground for resource.
  • Less chance to make mistake.
Cons
  • Extra clicks means slow in action.
  • It's adding cognitive load/decision overload.
  • In the majority of the case, resource owner won't have problem claim their ownership.
Hierarchical Authority Low Extra Low Extra High High
Description

Maximally enforces resource ownership by passing accountability up a fixed authority chain until someone claims it.

Pros
  • Clear chain of power to pass on.
  • Compliance audit friendly.
  • No need to think about reassign anymore.
Cons
  • Can potentially escalate all the way to the CEO — an outcome admins are rightfully concerned about.
  • Slows down the entire process; higher likelihood that some reviewers never respond.
Parallel Consensus Low Mid High Mid
Description

Requires simultaneous sign-off from two independent reviewers before ownership is confirmed.

Pros
  • Requires agreement from both reviewers, reducing single-point-of-failure ownership claims.
  • Both reviewers work in a single shared view — progress is visible to both sides.
Cons
  • May surface confidential resource information to a second-level reviewer who doesn't have the appropriate clearance.

Zooming Out

Where OA Sits in the Governance Lifecycle

Ownership has a lifecycle. OA is the attestation layer — but it has become the only layer that works. I chose to keep Assign, Discover, and Report out of this cycle. They're separate product investments — not mine to own. But seeing them clearly is what keeps my current scope honest, and my Run-stage thinking grounded.

01
Assign
Critical Gap
The compliance team identified that Okta has no effective central tool to manage ownership assignment. All downstream stages are built on this unstable foundation. Recommendation: deepen UX research into the current assign process and build a lightweight solution at minimum.
02
Discover
View Only
Resource Inventory has been built as a view-only page with potential to scale across resource types. Recommendation: explore Inventory as an intermediary platform — surfacing resources with missing or invalid owners and notifying the relevant stakeholders to take action.
03
Attest (OA)
Scope Expanding
The access certification team is currently owning both attestation and remediation. Engineering has raised whether this fundamentally shifts the problem we are solving — what began as a campaign flow has grown into a broader ownership governance challenge.
04
Remediate
Scope Exceeded
Since the team has already taken responsibility for remediation, the case for Governance Health becomes stronger — not just as a future vision, but as the natural direction this work is already heading toward.
